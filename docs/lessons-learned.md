# 项目经验归档

## 这次工作中确认有效的做法

### 1. 先锁定行为基线，再谈重构

最初偏离原版的核心原因，不是代码质量，而是参考基线本身不准确。后续切回以 [origin/AbyssalBlackjack.jsx](../origin/AbyssalBlackjack.jsx) 为唯一行为基线后，问题才真正收敛。

结论：

- 在复刻型项目里，第一优先级不是“重构得多漂亮”，而是“当前行为是否已经和基线一致”。
- 如果基线还没确认，就不应该过早做大规模架构设计。

### 2. `origin/` 必须保持只读

把 [origin/](../origin/) 当成只读参考区是正确决策。它让“原版是什么”与“现实现是什么”始终可比，避免在迁移和修复过程中失去对照物。

结论：

- 正式开发代码永远放在 [src/](../src/)。
- 原版参考文件只读，不参与正式功能开发。

### 3. 先做可运行迁移，再做分层抽离

这次更稳的路径不是从一开始就重写，而是：

1. 先把原版完整迁移进可运行 Web 项目。
2. 确认构建、预览、部署都正常。
3. 再按“纯规则 -> 调度时序 -> 视图组件”的顺序拆分。

结论：

- 对已有可运行原型做工程化，最安全的顺序是“保真迁移”优先于“架构美化”。

### 4. 分层拆分的推荐顺序已经验证有效

本项目验证过的拆分顺序如下：

1. 常量与卡牌/计分纯函数
2. 阶段发牌、结算、玩家动作纯状态变换
3. NPC 与 Joker 的时序调度 hook
4. 商店、附魔、推进流程 hook
5. 视图组件拆分

结论：

- 先纯函数，后流程，最后 UI，是当前项目最稳的拆分方式。
- 这样可以在每一步都保留可运行状态，并随时做构建验证。

### 5. 本地预览的“旧页面假象”很容易误导判断

曾经出现过 `127.0.0.1:4173` 仍显示旧 UI 与旧模块错误的情况，本质上是旧的预览实例和 HMR 状态残留，而不是当前代码真的回退了。

结论：

- 视觉复核时要优先使用新开的干净预览实例。
- 如果页面还在引用已删除模块，优先怀疑旧预览进程，而不是先怀疑代码。

### 6. GitHub Pages 问题经常不是代码问题

之前的 Pages 失败，根因并不是构建代码错误，而是仓库侧 Pages 配置尚未启用或未切到 GitHub Actions。

结论：

- 部署失败时要先区分“工作流失败”和“仓库配置未开通”。
- 本地 `npm run build` 通过，不等于 Pages 一定会自动上线。

### 7. `.js` 文件里不要直接写 JSX

在 [src/game/hooks/useProgressionFlow.js](../src/game/hooks/useProgressionFlow.js) 中一度直接写了 JSX 图标节点，导致 Vite 构建失败。虽然很快修掉，但这是标准的可避免错误。

结论：

- Hook 或工具文件如果保留 `.js` 后缀，就不要直接写 JSX。
- 要么改为 `createElement(...)`，要么把文件改成 `.jsx`。

### 8. 常量不能在拆 UI 时被硬编码回去

复核时发现 [src/components/game/ShopScreen.jsx](../src/components/game/ShopScreen.jsx) 中把 `MAX_HP` 语义硬编码成了 `5`。当前功能没坏，但这类问题说明“拆组件”很容易把原有约束丢回魔法数字。

结论：

- 拆视图时仍要保留关键规则常量的来源一致性。
- 视图层可以简单，但不能偷偷复制规则常量。

## 后续协作建议

- 每完成一次结构性拆分，都跑一遍构建和页面快检。
- 对“和原版是否一致”的讨论，优先用行为对照，不优先用主观感觉。
- 后续若继续移植到 Unity，应继续维持“规则层纯化、时序层适配、表现层独立”的边界。
